The brainstorm's AC 2 lists only `/cong-no-vt/tong-hop`, `/cong-no-vt/bao-cao-thang`, `/cong-no-vt/chi-tiet`. The plan turns this into "5 trang", which adds the two `cong-no-nc` pages, `getLaborWindowReport`, a labor filter change, widening the labor zod enum to include `thue_hd`, and an `allowedTypes` workaround on the NC grid. The planner-debate candidates came up with "5 trang" (candidate-1:9, candidate-2:12); the user never asked for it.
- **Failure scenario:** Labor accountants get a different URL contract (`?period=&y=&m=`), a different default on `chi-tiet`, and a server schema that accepts `thue_hd` on the contractor ledger while the UI hides it. Any NC regression ships on top of a VT-only feature. Phase 3 adds 4 extra files plus 2 service changes, about 2–3h of the 9h estimate.
- **Evidence:** brainstorm:41 (non-goal); brainstorm:51 (AC 2, VT-only paths). plan.md:21 "cho `cong-no-vt/{…}` và `cong-no-nc/{bao-cao-thang, chi-tiet}`". phase-03 "Modify `app/(app)/cong-no-nc/bao-cao-thang/page.tsx` + `bao-cao-thang-filter-nc.tsx`". phase-01 "Modify `lib/cong-no-vt/schemas.ts` và `lib/cong-no-nc/schemas.ts`: `z.enum(TRANSACTION_TYPES)`". - **Suggested fix:** Make the shared component changes additive: add an optional `periodLabel` to `MonthlyReport` and keep `year/month` as a fallback, and have `DetailReportFilter` accept an optional period slot. NC pages and services stay untouched. Leave `lib/cong-no-nc/schemas.ts` at 3 values. If the planner thinks NC parity is desirable, put it in "Câu hỏi chờ xác nhận" instead of the delivered scope.

## Finding 2: Classification module rewrites SQL that is already correct for `thue_hd`; half its API has no production consumer
- **Severity:** High
- **Location:** Phase 1 "Files to Create / Modify" (`transaction-classification.ts`), "Tasks & Steps" 1 and 3
- **Flaw:** Every signed CASE in the ledger already reads "`thanh_toan` → negative, ELSE positive", so `thue_hd` already gets the right sign with zero edits. Only the `= 'lay_hang'` predicates (summary/matrix FILTERs, monthly/detail period CASE, `balance-service` FILTER, the recon loop) need `IN ('lay_hang','thue_hd')`. The plan still replaces all of them with `signedSql/increaseSql/decreaseSql` built from `Prisma.raw` and a runtime column whitelist. It also ships `classifyAmount` and `signedAmount` as TS functions that no production file calls. The only consumer named in the plan is the unit test, which includes a "200 random seeded transactions" property test over those unused functions. That is a phantom test. The plan also exempts `lib/tai-chinh/*` because its identical "ELSE dương" CASE "đã đúng", then rewrites the same pattern inside `lib/ledger`, so its own rationale is inconsistent.
- **Failure scenario:** The CASEs at `ledger-aggregations.ts` 143–151 and 255–256 and `reconciliation-derive-service.ts` 95 are correct today and covered by the parity test `cong-no-luy-ke`. Rewriting them adds regression risk for no behavioral gain. A `Prisma.raw` column injection point is added where none existed before. Phase 1 step 3 relies on `cong-no-luy-ke` and the pilot already being green, and they are the only guards for the rewritten `queryCurrentBalance`.
- **Evidence:** `lib/ledger/ledger-aggregations.ts:143-151` (`WHEN 'thanh_toan' THEN -"totalTt" ELSE "totalTt"`), `:255-256` (same), `lib/vat-tu-ncc/reconciliation-derive-service.ts:95` (same). Predicates that actually need edits: `ledger-aggregations.ts:54-55, 164, 168, 307-308`, `lib/cong-no-vt/balance-report-service.ts:136, 140`, `lib/ledger/balance-service.ts:144`, `reconciliation-derive-service.ts:147`. Plan quote: "`classifyAmount(type, amount)`, `signedAmount(type, amount)` … tính chất `Σ signedAmount = Σ increase − Σ decrease` trên 200 giao dịch ngẫu nhiên". Debate table: "giữ nguyên `lib/tai-chinh/*` vì đã đúng".
- **Suggested fix:** Ship one constant file (`TRANSACTION_TYPES`, `TRANSACTION_TYPE_LABELS`, `DEBT_INCREASE_TYPES`, `PERIOD_LOCKED_TYPES`) plus one `Prisma.sql` fragment for `IN ('lay_hang','thue_hd')`. Edit only the `lay_hang` predicates. Delete `classifyAmount`, `signedAmount`, `signedSql`, the `col` whitelist, and the random property test. Keep the 5-path integration test (Bê tông HP 350.876.111), because it is the test that proves the behavior.

## Finding 7: `use-report-period-url.ts` is a generic URL-sync hook that the target filters do not fit
- **Severity:** Medium
- **Location:** Phase 3 "Files" (`components/ledger/use-report-period-url.ts`), Tasks 1
- **Flaw:** All three host filters build their URL explicitly when the user clicks Xem/Áp dụng, with a fixed key set. The hook is specified to read `useSearchParams`, `router.push` on change, and "giữ các tham số khác (`entityId`, `entityIds`, `projectIds`, `showZero`)". That conflicts with the plan's own description of `ReportPeriodSelector` as "controlled" and with `DetailReportFilter` "gửi params mốc … khi Áp dụng". The repo already has two period selectors with their own `pushParams` logic (`components/van-hanh/period-filter.tsx`, `components/tai-chinh/obligation-period-selector.tsx`). The hook would be a third URL-sync pattern.
- **Failure scenario:** On `chi-tiet`, a period change pushes immediately while Chủ thể/Công trình changes wait for Áp dụng. The page re-renders with half-applied filters, or the hook's "keep other params" logic overwrites filter state the user has not applied yet. This also adds `useSearchParams` and a Suspense requirement to two pages that do not use it today.
- **Evidence:** `app/(app)/cong-no-vt/bao-cao-thang/bao-cao-thang-filter.tsx:25-31` (explicit `new URLSearchParams()` on "Xem"); `components/ledger/detail-report-filter.tsx:83-89` (explicit build on apply, then `router.push(..., {scroll:false})`); existing selectors `components/van-hanh/period-filter.tsx:33-40`, `components/tai-chinh/obligation-period-selector.tsx:24-28`.
- **Suggested fix:** Export a pure `reportPeriodToParams(value)` from `lib/ledger/report-period.ts`. Each filter merges it into the URL it already builds on submit. Drop the hook file.
